# `robobench init` — Design Spec

**Date:** 2026-05-30
**Status:** Approved (brainstorming) — pending implementation plan
**Topic:** A `robobench init` command that scaffolds a starter `config.yaml`, giving new users a quick-import on-ramp instead of digging the campus-specific example out of `examples/`.

## Problem

A self-audit of onboarding found there is **no quick way for a user to get a
`config.yaml`**. The only template is `examples/campus_guide/code/config.yaml` —
buried four directories deep and campus-specific (13 building-named poses, a
`~/CS5335TurtleBot` workspace path). There is no `robobench init`, no top-level
template, and the README quick-start never shows how to create a config. For a
tool whose pitch is "connect any ROS2 robot," the very first step has friction.

(Audit also noted the example config carries `dds.rmw_implementation`, which
`load_adapter_config` does not read — a dead, misleading field.)

## Design decisions (resolved during brainstorming)

1. **Interaction model: commented template + optional flags** (no interactive
   prompts). robobench's CLI is entirely non-interactive argparse, and the
   test/CI environment is non-interactive; prompts would be inconsistent, hard
   to test, and would hang in CI. `robobench init` writes a commented
   `config.yaml`; `--ip` / `--ssh-user` / `--ssh-pass` / `--namespace` pre-fill
   the active fields when given, else placeholders are written.
2. **Template content: `robot`/`dds` active + optional sections commented.** The
   required `robot` and `dds` blocks are live; `workspace` / `build` / `launch`
   / `health` / `known_poses` appear commented with one-line explanations, so the
   single file doubles as inline schema documentation.
3. **Overwrite: refuse + `--force`.** If the target exists, refuse with a clear
   message and exit 2 unless `--force` is passed (never silently clobber a config).
4. **Output path: `--output`, default `./config.yaml`.**
5. **`rmw_implementation` is omitted** from the generated template (the loader
   ignores it; the dashboard/bridge hardcode `rmw_fastrtps_cpp`). This avoids
   generating a dead field without touching the loader.
6. **`init` does not take `--robot`** — it scaffolds a config file, it doesn't
   target a robot. (Other commands require `--robot turtlebot4`.)

## Architecture

A pure template-rendering function plus a thin CLI command. The function returns
the YAML text (active `robot`/`dds` filled from flags or placeholders, optional
sections commented). The command checks the output path, writes the text, and
prints a next-step hint. No network, no SSH, no rclpy.

```
robobench init [--ip .. --ssh-user .. --ssh-pass .. --namespace .. --output config.yaml --force]
  └─ _cmd_init:
       exists & not --force? -> "error: <path> exists (use --force)" exit 2
       else: render_config_template(ip=.., ssh_user=.., ssh_pass=.., namespace=..)
             -> write <output> -> print "wrote <path>" + next-step hint -> exit 0
```

## Components

### `src/robobench/config.py` — `render_config_template`
```python
def render_config_template(
    *,
    ip: str | None = None,
    ssh_user: str | None = None,
    ssh_pass: str | None = None,
    namespace: str | None = None,
    discovery_port: int = 11811,
) -> str: ...
```
- Pure (stdlib string building); no I/O. Returns the full YAML document text.
- Unset params render as placeholders: `ip` → `"192.168.x.x"`, `ssh_user` →
  `"ubuntu"`, `ssh_pass` → `"turtlebot4"`, `namespace` → `"turtlebot468"`.
- The active `robot` + `dds` sections it emits must parse and satisfy
  `load_adapter_config` (the required `robot.{ip,ssh_user,ssh_pass,namespace}` are
  present; `dds.discovery_port` is an int). Optional sections are commented out so
  they don't affect parsing.

The rendered document (placeholders shown):
```yaml
# robobench config — generated by `robobench init`.
# Required: the robot block. Everything else is optional (defaults shown).

robot:
  ip: "192.168.x.x"          # robot's IP on your LAN
  ssh_user: "ubuntu"
  ssh_pass: "turtlebot4"
  namespace: "turtlebot468"  # robot's ROS namespace

dds:
  discovery_port: 11811      # FastDDS Discovery Server port

# --- optional sections (uncomment + edit as needed) ---

# workspace:
#   dir: "~/my_ros2_ws"          # required for `robobench bringup` (colcon build)

# build:
#   packages: ["my_nav_pkg"]     # default: ["campus_nav_llm"]

# launch:
#   package: "my_nav_pkg"        # default: "campus_nav_llm"
#   file: "bringup.launch.py"    # default: "navigation_mode.launch.py"

# health:
#   user_input_topic: "/my_cmd"  # default: "/user_input"

# known_poses:                   # named poses for `robobench bringup --pose NAME`
#   home: { x: 0.0, y: 0.0, theta: 0.0 }
```

### `src/robobench/cli.py` — `init` subcommand + `_cmd_init`
- Subparser `init` with: `--ip`, `--ssh-user`, `--ssh-pass`, `--namespace`
  (all optional, default `None`), `--output` (default `"config.yaml"`),
  `--force` (store_true). No `--robot`.
- `_cmd_init(args)`:
  - `target = Path(args.output)`. If `target.exists() and not args.force` →
    `print(f"error: {target} already exists (use --force to overwrite)", file=sys.stderr)`
    and return 2.
  - Else write `render_config_template(ip=args.ip, ssh_user=args.ssh_user,
    ssh_pass=args.ssh_pass, namespace=args.namespace)` to `target`
    (`target.write_text(..., encoding="utf-8")`), print `f"wrote {target}"` and a
    next-step hint (e.g. `"next: edit it, then `robobench check` / `robobench
    dashboard --robot turtlebot4 --config {target}`"`), and return 0.

## Data flow & lifecycle
1. `robobench init` (optionally with flags) → renders + writes `config.yaml`.
2. User edits the file (or it's already filled from flags).
3. User runs `robobench check` / `dashboard` / `bringup` with `--config config.yaml`.

## Error handling
- Existing output without `--force` → clean error + exit 2 (no overwrite).
- Write failure (e.g. permission) → surfaces as an `OSError`; `main()`'s existing
  config-error handler already turns `FileNotFoundError`/`ValueError` into clean
  messages, but `OSError` on write would still traceback. This is an
  out-of-scope edge (writing to an unwritable path is rare for a scaffold
  command); not handled specially in v1.

## Testing strategy
- **`render_config_template` (pure):** defaults → output contains the placeholder
  strings; flags → output contains the supplied values; `yaml.safe_load(output)`
  succeeds (valid YAML); writing the output to a temp file and calling
  `load_adapter_config` on it returns the expected `ip`/`ssh_user`/`ssh_pass`/
  `namespace`/`discovery_port` (round-trip — proves the scaffold is a *usable*
  config, and that commented sections don't break parsing).
- **`_cmd_init` (CLI):** with `--output` in a tmp dir, returns 0 and the file
  exists with the rendered content; flags propagate into the file; a second run
  without `--force` returns 2 and leaves the file unchanged; with `--force`
  overwrites.
- All via `tmp_path`; no network, no SSH, no rclpy.

## Out of scope (YAGNI)
- No interactive prompts.
- No validation of the IP / credentials (scaffolding only — `robobench check`
  validates connectivity).
- No per-robot-type templates (the generic config works for TurtleBot4; future
  adapters can extend).
- No change to `load_adapter_config` (the `rmw_implementation` dead field is
  sidestepped by simply not generating it).

## Docs
- README "Quick start" gains `robobench init` as step 0 (`robobench init` →
  edit → run).
- `docs/tutorials/bringup-walkthrough.md`: replace "copy from
  `examples/campus_guide/code/config.yaml`" with `robobench init`.

## Honest caveats
- Pure-Python + file I/O; fully unit-testable, no hardware needed. (This command,
  unlike the SSH/DDS paths, has no hardware-only behavior — it's verifiable here
  end to end.)
